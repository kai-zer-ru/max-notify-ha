# [v2.3.0-beta2] — 2026-09-07

## Исправлено

- **Открытие настроек** notify.a161 больше не зависает надолго. Раньше окно ждало «слот» на запрос возможностей к серверу — иногда минутами, хотя сам запрос с компьютера и из Home Assistant проходит сразу.
- **Перезагрузка** этой интеграции тоже больше не тормозит по той же причине. Официальный API Max не затрагивался и как раньше открывается быстро.
- Срок автоотключения опроса больше не зажимается в **1–3 суток**. Если сервер дал 7 суток — показывается и используется 7.
- Запрос возможностей notify.a161 больше не уходит **дважды сразу** (из‑за этого сервер ставил второй в очередь и иногда отвечал 429). На один токен — один запрос, остальные ждут тот же ответ.

## Изменено

- При перезагрузке и при открытии настроек возможности **снова запрашиваются с сервера**, даже если они уже есть у клиента. Чаще лимита в минуту запросы не уходят (если сервер лимит не задал — не чаще одного раза в минуту). Если лимит ещё не подошёл — сразу берутся уже загруженные данные, без ожидания.
- Если сервер ответил не 200 — остаются уже полученные возможности, а если их ещё не было — значения по умолчанию. Паузу до следующего запроса задаёт ответ сервера (`rate_limit_capabilities_per_minute`); заголовок «повторить через N секунд» — минимальная пауза (если он больше лимита из JSON, ждём его).
- Заголовки (`X-RateLimit-Status`, `X-Retry-After-Seconds`) учитываются на опросе `/updates`, загрузке файлов и отправке: `REJECTED` / 429 — пауза из заголовка, `DELAYED` — не стучим чаще, чем сказал сервер.
- Для notify.a161 появился **WebSocket** (`wss://notify.a161.ru/ws/updates`): его выбираем по умолчанию, если сервер разрешил. При подключении сразу приходят накопившиеся события, новые — сами. Если сервер пишет, что выключается — клиент переподключается. В журнал пишется так же, как у опроса: старт и соединение — INFO, кадры, ping и переподключение — DEBUG. В настройках WebSocket снова есть шаг с кнопками. Смена режима сохраняется **до** перезагрузки, чтобы не оставался старый опрос.
- Входящие собщения больше **не перезагружают** интеграцию. Раньше каждое сообщение записывалось в настройки записи, Home Assistant считал это сменой конфигурации и через полсекунды перезагружал интеграцию.
- Короткий опрос раз в несколько секунд больше не используется. Если WebSocket нет, берём **Long Polling** (`wait` 5–60 с и `limit` задаются в настройках и уходят в `GET /updates`). Старые записи с обычным polling переключаются на Long Polling сами. В лог при старте пишутся `limit` и `wait`.
- Если токен неактивен — ни WebSocket, ни Long Polling не подключаем.
- Период автоотключения polling **больше не выбирается**. Срок задаёт сервер и показывается на отдельном информационном шаге — в тексте прямо написано, что значение с сервера. Подняли лимит на сервере — после обновления возможностей он применяется сам.
- В мастере и в настройках убраны лишние тексты: на каждом экране только то, что к нему относится. Автоотключение — на своём шаге, формат и режим — без чужих лимитов.

# [v2.3.0-beta1] — 2026-09-03

## Важно

- Для провайдера **notify.a161.ru** интеграция начинает опираться на ответ сервера **«возможности токена»** (`/me/capabilities`): что разрешено этому ключу прямо сейчас, какие лимиты и интервалы.
- **Официальный API Max** этим релизом не меняется: те же сценарии отправки и приёма, что и в 2.2.x.
- Это **beta**: поведение зависит от того, что реально отдаёт notify.a161.ru. Если сервер ещё не включил часть флагов (например WebSocket), соответствующие пункты в настройках просто не появятся.

## Добавлено

- Периодическое обновление возможностей с сервера (по умолчанию раз в сутки; интервал можно задать с сервера). При **перезагрузке** интеграции список возможностей запрашивается заново.
- Ограничение частоты запросов возможностей к серверу, чтобы не долбить API.
- Учёт лимитов **размера** фото / видео / документа с сервера: до загрузки файл проверяется по своему типу, в ошибке показывается актуальный потолок в МБ.
- Учёт лимитов **скорости** исходящих сообщений и загрузок файлов (паузы между отправками по правилам тарифа).
- Блокировка работы при **техработках** или **неактивном токене**, с понятным сообщением (если сервер его прислал).
- В мастере и в настройках показываются живые лимиты сервера: интервал опроса, размеры вложений, доступные форматы текста, источник данных (ответ API или запасные значения).
- Заготовка приёма входящих по **WebSocket**: режим появляется в списке только если сервер явно разрешил его для токена. Пока флаг выключен — как раньше, polling / только отправка.

## Изменено

- Формат сообщения (текст / Markdown / HTML), кнопки, группы, правка и удаление сообщений, типы вложений для **notify.a161** включаются или скрываются по флагам с сервера, а не «всё сразу из коробки».
- Интервал polling в настройках ограничен диапазоном, который прислал сервер (а не только жёсткими числами в клиенте).
- В мастере настройки: сначала токен и запрос возможностей, затем выбор **формата и режима приёма** уже по тому, что сервер разрешил.
- Рекомендуемый период автоотключения polling при долгом простое берётся с сервера; в интерфейсе по-прежнему выбор 1–3 суток.

## Исправлено

- Раньше Markdown/HTML могли быть отмечены как недоступные, но отправка с разметкой всё равно проходила. Теперь формат проверяется по возможностям токена.
- При слишком большом файле текст ошибки больше не опирается на общий «запасной» лимит, а показывает лимит **для этого типа** с сервера.
- В настройках больше не предлагаются форматы и режимы, которые сервер для токена отключил.

## Для пользователей beta

- После обновления откройте настройки интеграции notify.a161 и сохраните их ещё раз (или перезагрузите интеграцию), чтобы подтянуть свежие возможности.
- Проверьте отправку текста, при необходимости — фото/видео и отказ по размеру.
- Если что-то «вдруг запретилось» — смотрите описание шага настроек: там видно, что вернул сервер.

# [v2.2.0] — 2026-08-06

## Важно

- Исправлена **несовместимость с Home Assistant 2026.8.0.** В этом релизе HA изменили правило для устройств: один device больше нельзя привязывать сразу к нескольким вложенным записям (чатам). Старая схема MaxNotify — один общий device «на всю интеграцию» для всех чатов — из‑за этого ломалась: сущности notify пропадали или не находились, автоматизации получали ошибку вроде «Invalid MaxNotify entity», диагностика показывала «Неизвестно».
- Исправление сделано **по тому же принципу, что у встроенного Telegram Bot**: общий device самой интеграции + отдельный device на каждый чат/пользователя.
- Обновление **бесшовное** для уже настроенных записей: идентификаторы сущностей сохраняются, автоматизации и скрипты менять не нужно. После обновления интеграции запись конфигурации мигрирует на версию **1.3**.
- Один и тот же код работает и на **HA 2026.8+**, и на более старых Core (от `minimum_ha_version` 2026.2): на новых версиях используется актуальная привязка устройств, на старых — совместимый режим без дублей в интерфейсе.
- **После любого обновления Home Assistant Core** (не только до 2026.8) сторонняя интеграция **[Additional CA](https://github.com/Athozs/hass-additional-ca)** снова копирует сертификаты НУЦ Минцифры в контейнер. Пока SSL Context без них, MaxNotify к официальному API не подключается (`CERTIFICATE_VERIFY_FAILED`). Additional CA пишет / уведомляет: *CA … is missing in SSL Context. Home Assistant needs to be restarted* (для `russian_trusted_root_ca_pem.crt` и `russian_trusted_sub_ca_pem.crt`). Нужна **повторная перезагрузка** HA — это поведение Additional CA, не баг MaxNotify; предупреждение добавлено в README и в инструкцию по сертификатам.

## Исправлено

- После обновления HA до **2026.8.0** снова нормально создаются и находятся сущности notify по чатам.
- Убраны дубли устройств в карточке интеграции на HA 2026.7 и похожих версиях (когда один и тот же «MaxNotify» светился под каждым чатом).
- Устаревшие диагностические сенсоры (на уровне всей интеграции) остаются на общем device; сенсоры и уведомитель конкретного чата — на device этого чата.

## Изменено

- В интерфейсе Home Assistant каждый получатель (чат / пользователь) отображается как **отдельное устройство**, связанное с общим device интеграции.
- При загрузке интеграции раскладка устройств при необходимости восстанавливается сама (если после бэкапа или обновления HA что‑то «склеилось» обратно).

## Документация

- В **README** добавлено предупреждение: после обновления HA Core интеграция Additional CA заново ставит сертификаты, нужна **повторная перезагрузка**, иначе отправка в Max может не работать.
- В **docs/RUSSIAN_TRUSTED_CA.md** то же уточнение для способа через Additional CA.

# [v2.1.1] — 2026-07-28

## Важно

- **GET /chats** в официальном API Max больше не используется: с июня 2026 этот метод перестал отдавать диалоги. Отправка в личные чаты теперь работает напрямую через **`user_id`** (без предварительного получения `chat_id` диалога), как описано в документации Max (`POST /messages?user_id=...`).
- **`delete_last_outgoing_message`** для личных чатов отключён — этот метод работал только через `GET /chats`, который недоступен. Для групповых чатов (отрицательный `chat_id`) удаление последнего исходящего по-прежнему работает.
- Удалены неиспользуемые константы `API_PATH_CHATS` и `CHATS_PAGE_SIZE`.

## Изменено

- Функция **`resolve_message_url`** больше не вызывает `GET /chats` для личных диалогов — URL собирается сразу с `user_id`. Для групп и каналов по-прежнему используется `chat_id`.
- В подсказке об ошибке 403 при отправке по `user_id` уточнён порядок действий: для группы/канала нужно указать отрицательный `chat_id` из событий Max (WebHook / Long Polling) и настроить получателя как групповой чат.
- Из **README** убран раздел «Краткий журнал возможностей (по истории коммитов)» — информация дублировалась с основным changelog'ом.
- В **README** обновлён раздел «Где взять токен и ID»: указано, что `GET /chats` с июня 2026 недоступен, и описано, где брать `chat_id` группы (из событий `bot_added`, `message_created` при WebHook / Long Polling, либо из поля `chat_id` / `recipient_id` в событии `max_notify_received`).

## Документация

- **docs/RUSSIAN_TRUSTED_CA.md**: уточнён путь для сертификатов — теперь они копируются в `/config/additional_ca/` (а не в `/config/`), добавлен шаг про уведомление от Additional CA и перезагрузку HA. Добавлен раздел про различия официального Terminal & SSH (`core-ssh`) и community-дополнения SSH & Web Terminal, с пояснением про режим защиты и доступ к `docker`.

# [v2.1.0] — 2026-06-27

## Важно

- Официальный API Max переведён на новый адрес **`platform-api2.max.ru`** (вместо `platform-api.max.ru`) — по требованию платформы Max, дедлайн **19 июля 2026**.
- Новый сервер использует TLS-сертификаты **НУЦ Минцифры**. Если Home Assistant им не доверяет, интеграция с официальным API перестанет подключаться (ошибка SSL, «Не удалось подключиться»).
- **Порядок обновления:** сначала добавьте сертификаты в Home Assistant (на HAOS удобнее через [Additional CA](https://github.com/Athozs/hass-additional-ca)), перезапустите систему и убедитесь, что HTTPS к новому API работает — **затем** обновляйте MaxNotify до 2.1.0.
- Режим **notify.a161.ru** не менялся — для него эти шаги не нужны.

## Добавлено

- Подробная инструкция **[docs/RUSSIAN_TRUSTED_CA.md](https://github.com/kai-zer-ru/max-notify-ha/blob/master/docs/RUSSIAN_TRUSTED_CA.md)**: как установить сертификаты Минцифры на HAOS, Supervised, Docker, Core и других вариантах установки Home Assistant; как проверить SSL через `docker exec homeassistant` (не путать с обычным терминалом дополнения).
- В **README** — отдельный раздел про сертификаты и ссылка на инструкцию в содержании и в «Полезных ссылках».

## [1.4.11] — 2026-04-20

- **Slash-команды бота (официальный API Max):** в мастере настройки и в параметрах записи после шагов с кнопками клавиатуры — меню команд (добавление и удаление). Список синхронизируется с платформой при сохранении и при загрузке записи интеграции (аналог `setMyCommands` в API бота).
- **Входящие события:** если в тексте сообщения есть slash-команда (в том числе вариант с упоминанием бота вроде `@бот /команда`), для записи **официального API** в данных события `max_notify_received` поле **`update_type`** становится **`slash_command`**, чтобы в автоматизациях проще отличать такие сообщения от обычного текста.
- **Сенсоры идентификаторов сообщений по чатам:** для **каждого** настроенного получателя (отдельный чат или пользователь) создаются диагностические сенсоры **последнего входящего** и **последнего исходящего** `message_id`; состояние восстанавливается после перезапуска (**RestoreSensor**). Старые сенсоры «на всю запись интеграции» сохранены как **устаревшие**: они повторяют значение **только если** в записи настроен **ровно один** получатель (чтобы не смешивать id разных чатов).
- **Персистентное хранение** последних id сообщений и связанных маркеров в каталоге **`.storage`** Home Assistant — значения не теряются при перезапуске.

### Исправлено

- **notify.a161.ru и групповые чаты:** при первой настройке записи можно указать **отрицательный** `recipient_id` (**групповой** Chat ID), если у прокси связка выдана для группы, **или** положительный `user_id` для личного диалога; исходящие запросы для группы уходят с **`chat_id`**. У **`notify.a161.ru`** на одну выдачу ключа приходится **ровно один получатель**; **другой** чат или пользователь — это **другой API-ключ** и **отдельная** запись интеграции. В сервисах параметры **`chat_id` / `user_id` / `recipient_id`** для этого режима должны совпадать с **тем единственным** получателем, который зафиксирован при настройке (произвольное «перенаправление» в другой чат той же записью не поддерживается).
- **Сенсоры и запись исходящих id:** исправлена ситуация, когда идентификатор сообщения после успешной отправки не сохранялся и сенсоры не обновлялись: учёт **`subentry.data`** как отображаемого слоя (**`Mapping`**, не только **`dict`**, как в Home Assistant), более надёжный разбор **`message_id`** из ответа API (**`mid`** и др., запасной разбор текста ответа, снятие BOM).
- **Вызовы сервисов:** если не указан **`config_entry_id`**, запись MaxNotify может определяться по **`entity_id`** выбранных сущностей **`notify`** (удобно при нескольких интеграциях).

### Изменено

- Отправка через платформу **`notify`:** при явном **`recipient_id` / `chat_id` / `user_id`** в параметрах выполняется проверка по записи интеграции. Для **официального API** цель должна быть среди **настроенных** чатов и пользователей. Для **`notify.a161.ru`** допустим только **один** согласованный с токеном получатель (см. выше); иначе отправка отклоняется с понятной ошибкой.

- **README:** раздел про сенсоры `message_id`, уточнения по **`entity_id`**, **`config_entry_id`** и **`recipient_id`** для **`send_message`**, **`send_document`**, **`delete_message`**, **`edit_message`**.
- Обновлены **`services.yaml`**, строки интерфейса и переводы (**RU/EN**) под slash-команды, новые сенсоры и сообщения об ошибках.

## [1.3.1] — 2026-03-23

### Важно: как теперь работают кнопки под сообщением

С **1.3.1** правила **одинаковые** для текста, фото, документа, видео и для **редактирования** сообщения (когда вы задаёте поле с кнопками):

- Если включено **«Отправлять клавиатуру»** (так по умолчанию):  
  **не указали свои кнопки** в вызове — к сообщению подставляется **стандартная клавиатура** из настроек интеграции; **указали непустые свои кнопки** — к сообщению идут **только они**, без склейки со стандартной; **указали кнопки, но список пустой** — снова используется **стандартная** клавиатура из настроек.
- Если **«Отправлять клавиатуру»** выключено: стандартная клавиатура **не подставляется**; прикрепляются лишь **явно заданные** в вызове кнопки (если они не пустые).

Так проще предсказать результат в автоматизациях и не зависеть от того, какой именно сервис вы вызываете.

### Улучшено в интерфейсе Home Assistant

- Для **фото, документа, видео** и **редактирования сообщения** в формах сервисов появились **названия и пояснения** к переключателю «Отправлять клавиатуру» (русский и английский).
- Тексты подсказок для **кнопок** и клавиатуры **приведены в соответствие** с описанной выше логикой.

## [1.3.0] — 2026-03-22

### Важно: обязательно обновиться, если включён Long Polling

При приёме сообщений режимом **Long Polling** в прошлых версиях Home Assistant мог **долго ждать завершения загрузки** или писать в лог предупреждение о тайм-ауте при старте — как будто интеграция «висит» на этапе настройки.  
В **1.3.0** опрос сервера Max перенесён так, что он **не блокирует запуск** Home Assistant: после обновления система должна нормально дозагружаться, а входящие сообщения по-прежнему обрабатываются.

### Новое

- **Удаление сообщения** — отдельное действие сервиса: указали идентификатор сообщения и нужный чат/интеграцию, сообщение удаляется в Max. Удобно для автоматизаций «убрать старое меню».
- **Редактирование сообщения** — можно изменить текст, формат (обычный текст, Markdown или HTML), заменить или убрать кнопки под сообщением.
- **Свои кнопки к любой отправке** — при отправке текста, фото, документа или видео в дополнительных полях можно задать кнопки, которых нет в настройках интеграции (например, одноразовое меню для сценария). В версии **1.3.0** поведение склейки со стандартной клавиатурой различалось по сервисам; в **1.3.1** правила унифицированы (см. выше).
- **Больше попыток для тяжёлых файлов** — для фото, документа и видео можно указать, сколько раз повторять отправку, если сервер не сразу принял большой файл. Сами паузы между попытками работают предсказуемее.
- **Два сенсора на каждую интеграцию** — отдельно запоминается **последнее отправленное из Home Assistant** сообщение и **последнее входящее** (по данным приёма). Идентификатор в интерфейсе показывается **без префикса `mid.`**, чтобы проще копировать в автоматизации.
- **Примеры автоматизаций** — в репозитории добавлен отдельный файл с примерами вызовов сервисов и разбора входящих событий; в основном описании (README) есть на него ссылка.

### Улучшено

- В событии о входящем сообщении чаще и надёжнее передаётся **идентификатор сообщения**; для продвинутых сценариев доступны **полные данные**, которые прислал Max (чтобы ничего не «терялось» в упрощённом виде).
- Подписи к полям и сообщения об ошибках в интерфейсе Home Assistant дополнены там, где появились новые действия (в том числе на русском и английском).

### Исправлено

- Сенсор «последнее исходящее сообщение» мог оставаться пустым после отправки через сервис — теперь состояние обновляется и при вызове сервиса отправки, и при отправке через стандартное уведомление Home Assistant.
