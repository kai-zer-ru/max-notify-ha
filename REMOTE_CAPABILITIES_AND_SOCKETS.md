## 1. Введение и цели

Сервис notify.a161.ru переходит на платную модель с тарифами и ограничениями, а также планирует отказаться от `GET /updates` в пользу сокетов.

Сейчас лимиты, интервалы и набор возможностей **зашиты в клиенте**. Любое изменение на стороне API требует релиза интеграции Home Assistant.

### Зачем нужен remote capabilities

Клиент периодически запрашивает у API описание того, что разрешено **этому токену прямо сейчас**:


| Цель                                  | Результат                                 |
| ------------------------------------- | ----------------------------------------- |
| Менять лимиты по тарифу               | Без релиза HA                             |
| Отражать оплату / блокировку входящих | Явные флаги `update_available` / `websocket_available`, а не угадывание по HTTP-кодам |
| Сообщить доступные каналы приёма      | `polling`, `webhook`, `websocket` или ничего |
| Плавно отключить `/updates`           | `deprecation` + `receive_modes`           |
| Сменить URL/параметры WS              | Поля в capabilities, не хардкод           |


### Зачем отдельно специфицировать WebSocket

Домашний Home Assistant почти всегда за NAT/CGNAT. Поэтому входящие по сокету доставляются только через **исходящий** WebSocket с хоста на API (`wss://…`). Параметры соединения приходят из capabilities.

## 2. Текущее поведение клиента

Краткий снимок того, что клиент делает сегодня (без remote config).


| Параметр                   | Значение в клиенте                     |
| -------------------------- | -------------------------------------- |
| Base URL                   | `https://notify.a161.ru`               |
| Версия API (query `v`)     | `1.2.5`                                |
| Приём входящих             | Только short polling `GET /updates`    |
| Интервал polling           | 2–30 с (по умолчанию 5)                |
| `limit` в `/updates`       | `5`                                    |
| Макс. размер upload        | 10 MiB (общий на photo/video/document) |
| Пауза между успешными send | ≥ 1 с                                  |
| Режимы receive             | `send_only`, `polling`                 |
| WebSocket                  | не реализован                          |


Входящие нормализуются и публикуются в шину HA как событие `max_notify_received`.

## 3. Эндпоинт capabilities

### 3.1. Контракт

Отдельный ресурс:

```http
GET /me/capabilities HTTP/1.1
Host: notify.a161.ru
Authorization: <access_token>
```

Ответ — JSON. Поля, неизвестные клиенту, игнорируются.

### 3.2. Общие требования к ответу


| Требование     | Описание                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| Per-token      | Лимиты и флаги считаются для токена из `Authorization`, а не глобально «на всех»                                   |
| Актуальность   | `update_available`, `websocket_available` и флаги пересчитываются на каждый запрос                               |
| Кэш на клиенте | HA кэширует ответ и обновляет при setup/reload, по TTL (`refresh_capabilities`) и при `402` / `403` / `429`. Статус **не 200** — оставить прошлый снимок; если снимка не было — безопасные defaults. |
| Заголовки лимита | `X-RateLimit-Status`: `PASSED` (сразу), `DELAYED` (200, но запрос стоял в очереди), `REJECTED` (вместе с **429**). `X-Retry-After-Seconds` — **минимальная** пауза до следующего GET. Основной интервал — `rate_limit_capabilities_per_minute` из JSON: он приоритетнее, если строже заголовка. |
| Один запрос | На один токен клиент не шлёт параллельные GET: второй вызывающий ждёт тот же ответ. |


### 3.3. Обязательные поля схемы


| Поле                | Тип              | Обязательность                    |
| ------------------- | ---------------- | --------------------------------- |
| `update_available`     | boolean          | да                                |
| `websocket_available`  | boolean          | да                                |
| `receive_modes`        | string[]         | да                                |
| `max_photo_size`    | integer (**МБ**) | да (если photo поддерживается)    |
| `max_video_size`    | integer (**МБ**) | да (если video поддерживается)    |
| `max_document_size` | integer (**МБ**) | да (если document поддерживается) |

Единица измерения для `max_photo_size`, `max_video_size`, `max_document_size` — **мегабайты (МБ)**, целое число. Пример: `10` означает 10 МБ.

Остальные поля — по мере готовности API; клиент использует safe defaults, если поля нет.

## 4. Справочник полей

Имена ниже — предложение. Можно переименовать при согласовании; менять смысл нежелательно.

Для каждого поля:

- **Тип** — ожидаемый JSON-тип  
- **Назначение** — что означает на стороне API  
- **Использование в HA** — как клиент на это опирается  
- **Зачем API** — выгода для провайдера

### 4.1. Лимиты вложений и доступность входящих

#### `max_photo_size`


|                        |                                                                                                                               |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Тип**                | `integer` (**мегабайты, МБ**)                                                                                                 |
| **Назначение**         | Максимальный размер одного изображения, который API примет при upload / send photo.                                           |
| **Использование в HA** | Проверка размера файла **до** upload. При превышении — понятная ошибка пользователю без лишнего трафика и без отказа сервера. |
| **Зачем API**          | Менять лимит по тарифу без релиза клиента. Сейчас в HA зашито ~10 МБ на все типы.                                             |
| **Пример**             | `10` (10 МБ)                                                                                                                  |


#### `max_video_size`


|                        |                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| **Тип**                | `integer` (**мегабайты, МБ**)                                                             |
| **Назначение**         | Максимальный размер одного видеофайла.                                                    |
| **Использование в HA** | Pre-check перед upload video (отдельный порог от photo/document).                         |
| **Зачем API**          | Дорогие по хранению/трафику видео можно ограничивать жёстче или только на платных планах. |
| **Пример**             | `50` (50 МБ)                                                                              |


#### `max_document_size`


|                        |                                                                              |
| ---------------------- | ---------------------------------------------------------------------------- |
| **Тип**                | `integer` (**мегабайты, МБ**)                                                |
| **Назначение**         | Максимальный размер одного документа (`type=file` / send document).          |
| **Использование в HA** | Pre-check перед upload; сообщение вида «файл больше N МБ по лимиту сервиса». |
| **Зачем API**          | Отдельно регулировать документы, не смешивая с медиа.                        |
| **Пример**             | `10` (10 МБ)                                                                 |


#### `update_available`


|                        |                                                                                                                                                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Тип**                | `boolean`                                                                                                                                                                                                                                 |
| **Назначение**         | Разрешён ли этому токену приём входящих через **polling** (`GET /updates`) и **webhook**. Зависит от тарифа и состояния оплаты конкретного пользователя.                                                                                 |
| **Использование в HA** | `true` — можно держать polling/webhook из `receive_modes` и публиковать `max_notify_received`. `false` — остановить polling и webhook; send-only по входящим через эти каналы, repair/уведомление с текстом `status_message`.         |
| **Зачем API**          | Явно сообщить «polling/webhook отключены» (неуплата, тариф), без угадывания по HTTP-кодам на `/updates`.                                                                                                                                  |
| **Пример**             | `true` / `false`                                                                                                                                                                                                                          |


#### `websocket_available`


|                        |                                                                                                                                                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Тип**                | `boolean`                                                                                                                                                                                                                                 |
| **Назначение**         | Разрешён ли этому токену приём входящих через **WebSocket**. Зависит от тарифа и состояния оплаты; может отличаться от `update_available` (например polling уже отключён, WS ещё доступен, или наоборот).                              |
| **Использование в HA** | `true` — можно открыть исходящий WSS на `websocket_url` (если `"websocket"` ∈ `receive_modes`). `false` — не коннектиться к WS, закрыть существующее соединение; repair/уведомление с `status_message`.                                   |
| **Зачем API**          | Отдельно управлять доступностью сокетов при миграции с `/updates` и при разных тарифах, без смешения с polling/webhook.                                                                                                                  |
| **Пример**             | `true` / `false`                                                                                                                                                                                                                          |


Рекомендации:

- при `update_available: false` не включать в `receive_modes` значения `polling` и `webhook` (или клиент считает их недоступными);
- при `websocket_available: false` не включать в `receive_modes` значение `websocket`;
- если оба `false` — `receive_modes: []`, входящие полностью недоступны.

### 4.2. Rate limits

#### `max_requests_per_second`


|                        |                                                                                                        |
| ---------------------- | ------------------------------------------------------------------------------------------------------ |
| **Тип**                | `number` (int или float)                                                                               |
| **Назначение**         | Допустимая частота HTTP-запросов к API для этого токена (или аккаунта — зафиксировать в описании API). |
| **Использование в HA** | Локальный pacing исходящих HTTP-вызовов, чтобы реже ловить `429`.                                      |
| **Зачем API**          | Крутить лимит по тарифу централизованно.                                                               |
| **Пример**             | `5`                                                                                                    |
| **Уточнить**           | Окно (sliding 1 с / fixed); входят ли только write-методы; действует ли отдельно от WebSocket-кадров.  |

### 4.3. Каналы приёма входящих

#### `receive_modes`


|                         |                                                                                                                   |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Тип**                 | `string[]`                                                                                                        |
| **Назначение**          | Какие каналы доставки входящих API готов обслуживать для этого токена **сейчас**.                                 |
| **Допустимые значения** | Только из набора `["polling", "webhook", "websocket"]`. Пустой массив `[]` — входящие недоступны.                 |
| **Использование в HA**  | UI и runtime выбирают режим только из этого списка. Дополнительно: `polling`/`webhook` требуют `update_available: true`, `websocket` — `websocket_available: true`. |
| **Зачем API**           | Явно объявить, какие транспорты живы для токена; мягкая миграция (например сначала все три, потом без `polling`). |
| **Пример**              | `["polling", "webhook", "websocket"]`                                                                             |

Смысл значений:

- `polling` — HTTP polling (`GET /updates` или путь из `updates_url`);
- `webhook` — **опциональный канал (может быть добавлен позже):** API шлёт входящие HTTP `POST` на публичный URL клиента (HA). Нужен доступный с интернета адрес (reverse proxy, Nabu Casa, tunnel). Значение **остаётся в наборе** `receive_modes`, чтобы включить поддержку в клиенте без смены контракта capabilities;
- `websocket` — исходящий WSS (клиент → API).


#### `updates_url`


|                        |                                                                                                            |
| ---------------------- | ---------------------------------------------------------------------------------------------------------- |
| **Тип**                | `string` (path или абсолютный URL на API host)                                                             |
| **Назначение**         | Endpoint для polling, пока режим `polling` жив.                                                            |
| **Использование в HA** | Вместо захардкоженного `/updates`.                                                                         |
| **Зачем API**          | Переезд на `/v2/updates` без релиза клиента.                                                               |
| **Пример**             | `"/updates"`                                                                                               |
| **Ограничение**        | Клиент примет только path на известном API host (или allowlist). Произвольный URL в интернет — нет (SSRF). |


#### `updates_limit`


|                        |                                                                                |
| ---------------------- | ------------------------------------------------------------------------------ |
| **Тип**                | `integer`                                                                      |
| **Назначение**         | Рекомендуемый или максимальный query-параметр `limit` (число update за ответ). |
| **Использование в HA** | Подстановка в polling-запрос (сейчас `5`).                                     |
| **Зачем API**          | Баланс нагрузки: размер пачки vs частота запросов.                             |
| **Пример**             | `5`                                                                            |


#### `updates_interval_min` / `updates_interval_max` / `updates_interval_default`


|                        |                                                                                |
| ---------------------- | ------------------------------------------------------------------------------ |
| **Тип**                | `integer` (секунды), три отдельных поля                                        |
| **Назначение**         | Допустимый диапазон и значение по умолчанию для паузы между polling-запросами. |
| **Использование в HA** | Кламп настройки пользователя (сейчас min 2, max 30, default 5).                |
| **Зачем API**          | При нагрузке поднять минимум интервала для всех клиентов одной сменой ответа.  |
| **Пример**             | `2` / `30` / `5`                                                               |


#### `websocket_url`


|                        |                                                                                                                              |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **Тип**                | `string` (`wss://…`)                                                                                                         |
| **Назначение**         | Адрес WebSocket для приёма входящих.                                                                                         |
| **Использование в HA** | При режиме `websocket` клиент **сам** открывает исходящее соединение на этот URL (см. [§6](#6-доставка-входящих-websocket)). |
| **Зачем API**          | Смена хоста, path, региона без релиза HA.                                                                                    |
| **Пример**             | `"wss://notify.a161.ru/ws/updates"`                                                                                          |


#### `websocket_protocol` / `websocket_api_version`


|                        |                                                                                                              |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Тип**                | `string` (+ опционально вторая `string`)                                                                     |
| **Назначение**         | Идентификатор протокола WebSocket-транспорта (subprotocol / `json-v1`) и версия **служебных** кадров (auth, ping, error). Payload кадра `update` **не** версионируется отдельно — см. §6.3. |
| **Использование в HA** | Выбор парсера служебных кадров. Неизвестная версия → явный отказ с просьбой обновить интеграцию.                                                                                              |
| **Зачем API**          | Эволюция handshake/keepalive без смены формата входящих update.                                                                                                                               |
| **Пример**             | `"json-v1"`, `"1"`                                                                                           |


#### `websocket_heartbeat_seconds`


|                        |                                                                                     |
| ---------------------- | ----------------------------------------------------------------------------------- |
| **Тип**                | `integer` (секунды)                                                                 |
| **Назначение**         | Ожидаемый интервал keepalive (WebSocket ping/pong или application-level heartbeat). |
| **Использование в HA** | Клиент шлёт/ждёт heartbeat; при тишине дольше порога — reconnect.                   |
| **Зачем API**          | Согласовать поведение с idle timeout балансеров/прокси.                             |
| **Пример**             | `30`                                                                                |


#### `websocket_reconnect_min_seconds` / `websocket_reconnect_max_seconds`


|                        |                                                                                                      |
| ---------------------- | ---------------------------------------------------------------------------------------------------- |
| **Тип**                | `integer` (секунды)                                                                                  |
| **Назначение**         | Коридор exponential backoff при переподключении после обрыва (не для фатальных ошибок вроде unpaid). |
| **Использование в HA** | Backoff строго внутри `[min, max]`, чтобы при outage не устроить thundering herd.                    |
| **Зачем API**          | Централизованный антишторм reconnect.                                                                |
| **Пример**             | `2` / `120`                                                                                          |


#### `websocket_auth`


|                        |                                                                                          |
| ---------------------- | ---------------------------------------------------------------------------------------- |
| **Тип**                | `object`                                                                                 |
| **Назначение**         | Как клиент должен авторизоваться на WebSocket. Клиент не угадывает схему.                |
| **Возможные варианты** | токен в query; заголовок при HTTP Upgrade; первый кадр `auth` после connect.             |
| **Использование в HA** | Ровно один способ, описанный объектом.                                                   |
| **Зачем API**          | Смена схемы auth (например убрать токен из query из‑за логов прокси) через capabilities. |
| **Пример**             | см. [§5](#5-пример-ответа)                                                               |

### 4.5. Операционные и UX-поля

#### `inactivity_auto_disable_days`


|                        |                                                                                                                                      |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Тип**                | `integer` (дни) или `null`                                                                                                           |
| **Назначение**         | Через сколько дней без входящей активности / без кнопок отключить **Long Polling** (send-only). `null` — не требовать auto-disable. WebSocket этим полем не трогаем. |
| **Использование в HA** | Только режим Long Polling. Срок с сервера (`polling_inactivity_auto_disable_days` или этот alias). WebSocket не переключаем. |
| **Зачем API**          | Меньше вечных idle GET /updates у забытых установок.                                                                                   |


#### `maintenance` / `status_message`

| **Пример**             | `true`, `"Работы до 23:00 UTC"`                                                          |

## 6. Доставка входящих: WebSocket

### 6.1. Направление соединения

Единственная модель для WebSocket: **исходящее соединение клиента к API**.

- Home Assistant (интеграция) сам открывает `wss://…` на `websocket_url` из capabilities.
- Сервер **не** инициирует соединение к хосту пользователя.
- Исходящие WSS обычно проходят за NAT/CGNAT без проброса портов и без публичного URL HA.

Параметры соединения (`websocket_url`, auth, heartbeat, reconnect) приходят из `GET /me/capabilities`.

### 6.2. Жизненный цикл на стороне HA

1. Загрузить capabilities.
2. Если `websocket_available != true` или `websocket` ∉ `receive_modes` — не коннектиться к WS.
3. Открыть `wss` на `websocket_url`, авторизоваться по `websocket_auth`.
4. Держать соединение: heartbeat по `websocket_heartbeat_seconds`.
5. На кадр `update` — та же нормализация, что для `/updates` → событие `max_notify_received`.
6. На обрыв — reconnect с backoff в `[websocket_reconnect_min_seconds, websocket_reconnect_max_seconds]`.
7. На `auth_fail` с причиной unpaid/revoked — остановить цикл, refresh capabilities, показать `status_message` (если есть).
8. На `capability_changed` — немедленно refetch capabilities.

Для polling/webhook: если `update_available != true` или канал ∉ `receive_modes` — не запускать соответствующий приём.

Фактический протокол (2026-09): `wss://notify.a161.ru/ws/updates`, заголовок `Authorization`. Клиент также шлёт `X-Client-Version: МАЖОР.МИНОР` (из версии интеграции HA, без патча: `2.3.0-beta3` → `2.3`) на HTTP и WebSocket. При подключении сервер сразу отдаёт накопленное (массив или кадры), дальше — push. Клиент шлёт `{"cmd":"ping"}` (в ответ пустой массив или недошедшие updates). `{"error":"invalid json"}` — лог, соединение живое. `{"type":"closed","reason":"server shutting down"}` — переподключение. `token_active=false` — не коннектиться. Long polling: `GET /updates?limit=&wait=`; `wait` всегда `polling_interval_default_s` в пределах `polling_interval_min_s`…`polling_interval_max_s`. `polling_interval_s` — старый короткий опрос, клиент его не использует. Автоотключение на send-only (`polling_inactivity_auto_disable_days`) — только для Long Polling, не для WebSocket.

### 6.3. Минимальный протокол кадров

Текстовые JSON-кадры (или эквивалент). Точные имена negotiable.

#### Формат кадра `update` (обязательно)

JSON внутри кадра `update` **должен совпадать** с JSON одного элемента массива ответа `GET /updates` — тот же объект, без обёртки и без отдельной схемы envelope.

Клиент использует **один и тот же** парсер/нормализатор для polling и WebSocket. Отдельная версия payload для WS не предусмотрена.

Пример (иллюстративно): если `/updates` отдаёт `{"updates":[{"update_type":"message_created",...}]}`, то кадр `update` содержит ровно `{"update_type":"message_created",...}` — один такой объект на кадр.


| Кадр                 | Направление     | Назначение                                                                                                             |
| -------------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `auth`               | client → server | Если `websocket_auth.method = first_frame`                                                                             |
| `auth_ok`            | server → client | Успешная авторизация                                                                                                   |
| `auth_fail`          | server → client | Отказ: `token` / `unpaid` / `revoked` + опционально `message`                                                          |
| `update`             | server → client | Входящее обновление; JSON **идентичен** одному элементу из ответа `GET /updates` (§6.3)                              |
| `ping` / `pong`      | оба             | Keepalive (либо стандартный WebSocket control ping)                                                                    |
| `error`              | server → client | Протокольная ошибка                                                                                                    |
| `capability_changed` | server → client | Сигнал перечитать capabilities                                                                                         |
| `cursor` / `marker`  | оба             | Опционально: резюм после reconnect, чтобы не потерять update                                                           |


Внутренний контракт HA (`max_notify_received`) менять не планируется: меняется только транспорт до нормализации.

### 6.4. Связь с capabilities

Для запуска WS без релиза под каждую правку инфраструктуры в ответе capabilities должны быть как минимум:

- `update_available` / `websocket_available`
- `receive_modes` (включая `"websocket"` при `websocket_available: true`)
- `websocket_url`
- `websocket_protocol` / `websocket_api_version`
- `websocket_auth`
- `websocket_heartbeat_seconds`
- `websocket_reconnect_min_seconds` / `websocket_reconnect_max_seconds`

## 7. Поведение клиента Home Assistant

1. **Fetch** capabilities при setup entry, reload, по TTL кэша и при `402` / `403` / `429` (и по `capability_changed` с WS). Параллельные вызовы на один токен — один HTTP.
2. **Кэш** в runtime данных config entry; UI options и валидация сервисов читают кэш. Ответ не 200 — прошлый снимок или defaults. Паузу берём из JSON (`rate_limit_capabilities_per_minute`), `X-Retry-After-Seconds` только как пол.
3. **Лимиты файлов** — из `max_*_size` (+ локальный fallback, если поля нет).
4. **Feature flags** — гейты сервисов edit/delete/send_*.
5. **`update_available: false`** — остановить polling и webhook; **`websocket_available: false`** — остановить WS. Если оба `false` — send-only по входящим; repair + `status_message`.
6. **Webhook** — если `"webhook"` ∈ `receive_modes` и `update_available: true`, клиент может предложить режим webhook (когда поддержка будет реализована). Требует публичного URL HA; до реализации канал игнорируется, но остаётся в контракте.
7. **Safe defaults** — при недоступности capabilities или старом API клиент продолжает работать на встроенных константах (§2).
8. **Неизвестные ключи** — игнорировать.

## 8. Миграция с GET /updates

Рекомендуемая последовательность на стороне API:


| Этап            | `receive_modes`              | Поведение                                                  |
| --------------- | ---------------------------- | ---------------------------------------------------------- |
| 0. Сейчас       | `["polling"]` (фактически)   | Только `/updates`                                          |
| 1. Dual-run     | `["polling", "websocket"]`   | Оба канала; в `deprecation.polling` — дата отключения      |
| 2. WS preferred | то же + уведомления клиентам | HA предлагает/переключает на websocket                     |
| 3. Polling off  | `["websocket"]`              | `/updates` отключён или отвечает явной ошибкой deprecation |


Клиент на этапе dual-run может оставить polling как fallback, если WS недоступен, пока `"polling"` присутствует в `receive_modes`.

## 9. Ограничения и безопасность

**Не следует отдавать в capabilities:**

- секреты, чужие токены, произвольный executable config;
- произвольный `base_url` / redirect на чужой host без allowlist (риск SSRF и подмены API).

**Допустимо:**

- path на том же API host (`updates_url`);
- `wss://` на ваших доменах (`websocket_url`);

**Нагрузка:**

- не ожидать capabilities на каждый send; клиент кэширует;
- при массовом outage опираться на `websocket_reconnect_*`, а не на мгновенный reconnect всех клиентов.

### P0 — необходимо для тарифов и отказа от polling без хаоса

- `update_available`, `websocket_available` (+ `status_message`)

- feature flags (`supports_*`)
- `deprecation` для polling

- `inactivity_auto_disable_days`
- `maintenance` / `status_message` (если не сделали в P0)

### Транспорт

1. Спроектировать и задокументировать **outbound WebSocket** (HA → API) как замену `/updates`.
2. Держать dual-run, пока в `receive_modes` есть и `polling`, и `websocket`.
